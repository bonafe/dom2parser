Escopo e fronteira do projeto

O DOM2parser é uma biblioteca de compressão, não um gerador de parsers. Ele recebe HTML e devolve uma representação estrutural compacta (texto ou JSON). Um programa externo — que tem seu próprio LLM — consome essa representação, gera o parser (CSS/XPath/lxml/BeautifulSoup) e o valida contra o HTML original, nunca contra a versão compactada.

HTML original │ ▼ ┌─────────────────────────────┐ │ DOM2parser │ ← este projeto │ (7 etapas, ver abaixo) │ └─────────────────────────────┘ │ ▼ Representação compacta (texto/JSON) │ ▼ ┌─────────────────────────────┐ │ Programa consumidor │ ← fora do escopo │ (LLM → parser → validação)│ └─────────────────────────────┘ │ ▼ Parser executado no HTML ORIGINAL completo

O pipeline de 7 etapas

1 · Sanitização estrutural

Remove script, style, svg, noscript, comment, meta, link e trunca data-URIs inline. Atributos ruidosos (style, handlers on*, atributos visuais legados como bgcolor/cellpadding) são removidos por denylist, não allowlist — mais seguro que arriscar descartar um data-* customizado que uma etapa posterior precise.

Também remove navegação/menus/sidebars/breadcrumbs (por tag, role ou palavra-chave em classe/id) e widgets ocultos por display:none inline — mas nunca por atributo hidden ou classe de ocultação via CSS externo, porque sites reais usam isso para paginação client-side de conteúdo real (ver decisão sobre paginação oculta).

2 · Dedup de subtree idêntico

Colapsa subtrees byte-a-byte idênticos repetidos em escala (ex. um ícone SVG de compartilhar repetido 484× num site de notícias) num único exemplar + contagem. Limiar de contagem propositalmente alto — ver por quê.

3 · Fingerprint estrutural com fallback

Assinatura por elemento, numa cadeia de prioridade:

data-testid → role/aria-* → classes semânticas → id → tag + forma dos filhos

Classes CSS "atômicas" (estilo Stylex/CSS-in-JS, ex. x78zum5) e atributos de hash de build uniformes (ex. data-v-444d5111 do Vue scoped CSS) são detectados e ignorados na comparação — são artefatos de compilação, não identidade semântica.

4 · Content signature

Cada campo de texto é classificado sempre a partir do próprio texto, nunca da classe CSS:

Temporais
DATE DATETIME TIME
Numéricos
MONEY CURRENCY INTEGER DECIMAL PERCENTAGE
Estruturados
EMAIL URL PHONE BOOLEAN
Específicos do projeto
FILE_FORMAT COUNT_LABELED
Genéricos
TEXT EMPTY

Degrada graciosamente: texto que não bate em nenhum padrão específico vira TEXT (nunca força um tipo errado nem lança exceção).

5 · Clusterização tolerante

Dois níveis, porque estrutura DOM sozinha não basta:

  1. Estrutural — agrupa por fingerprint. Campos opcionais não fragmentam o grupo (um card sem selo de qualidade continua no mesmo cluster dos outros 9).
  2. Por assinatura de conteúdo — dentro de um grupo estrutural idêntico, sub-agrupa pela sequência de tipos dos filhos diretos. É assim que uma linha de transação (DATE|TEXT|CURRENCY|MONEY) se separa de uma linha de categoria (EMPTY|TEXT|EMPTY|EMPTY) mesmo quando ambas são tr(td,td,td,td) sem nenhuma classe distintiva.

6 · Ranking de relevância

O componente mais heurístico do projeto. Contagem bruta de repetição não indica relevância — um menu de navegação rotineiramente se repete mais que a tabela de dados real. O score combina:

  • Diversidade de tipos de conteúdo informativos (campos com DATE/MONEY/etc. pontuam mais que TEXT/EMPTY puros)
  • Número de sub-campos semanticamente distintos por registro
  • Palavras-chave de contêiner ancestral (bônus: result/row/item; penalidade: nav/menu/sidebar)
  • Tamanho de texto do próprio registro (log-amortecido)

Todos os sinais são limitados em profundidade (3 níveis) — um sinal recursivo irrestrito faria um contêiner genérico grande "herdar" a riqueza de tudo que está aninhado dentro dele e vencer o registro real que ele envolve.

7 · Sampling representativo

Primeiro, segundo, meio, penúltimo, último — mais outliers reais: valor numérico mínimo/máximo por campo (ex. o maior débito de uma fatura) e o registro com texto mais curto/mais longo.

Formato de saída

Exemplo real gerado a partir de uma fatura de cartão (ver todos os resultados):

REPEATED STRUCTURES (ranked by relevance):

tr > td > div.lancamentos > table > tbody > tr
  count: 122
  signature: DATE | TEXT | CURRENCY | MONEY
  examples:
    ['28/07', 'PGTO DEBITO CONTA 6937 000000253 200211', 'R$', '-11.966,18']  # numeric-outlier
    ['03/08', 'OBA HORTIFRUTI INDAIAT INDAIATUBA BR', 'R$', '99,97']          # representative-position
    ...

O formato JSON equivalente carrega os mesmos campos (path, count, signature, examples, optional_fields, rank_score) — veja a referência da API.
