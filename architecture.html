Escopo e fronteira do projeto

O DOM2parser recebe HTML e devolve três coisas a partir de uma única passagem pelo pipeline: uma representação estrutural compacta em texto, a mesma informação em JSON, e um parser verificado (ParserSpec) pronto para extrair os registros do documento original. As três nascem do mesmo compress() — nenhuma é derivada de outra depois, e por isso não podem discordar sobre o que foi encontrado.

A biblioteca não chama nenhum LLM. A síntese do parser é uma busca determinística: como a biblioteca tem em mãos os elementos-alvo (não apenas amostras deles), escolher um seletor é uma pergunta que se mede — gera candidatos, roda cada um contra o documento, fica com o que comprovadamente alcança todos os registros — em vez de uma pergunta que se chuta. Um modelo consumindo só a forma compacta veria sete exemplos e um path truncado; a biblioteca vê o documento inteiro. Para esse trabalho específico, medir é estritamente melhor que adivinhar.

HTML original │ ├─────────────────────────────────────────┐ ▼ │ ┌─────────────────────────────┐ │ │ Fases 1-7: encontrar │ │ │ as estruturas repetidas │ │ └─────────────────────────────┘ │ │ │ ▼ │ Representação compacta (texto/JSON schema 2) │ │ │ ▼ │ ┌─────────────────────────────┐ │ │ Fases I-M: sintetizar │ │ │ e verificar o parser │ │ │ (ancoragem → registro → │◄─────────────┘ │ campos → ParserSpec) │ mede os candidatos └─────────────────────────────┘ contra o original │ ▼ ParserSpec (YAML/JSON) ── executor ──► registros extraídos do HTML ORIGINAL

A única parte genuinamente semântica — nomear um campo — também não usa modelo: os nomes são lidos da própria página (linha de cabeçalho, th, itemprop, data-testid, classe), com queda para tipo e posição quando a página não diz nada. Um seletor que casa demais sem que haja regra de conteúdo explicando a sobra nunca vira registro — vai para failures com os candidatos que chegaram mais perto. Parser que funciona pela metade é indistinguível de parser que funciona, e pior que parser nenhum.

Parte 1 — Encontrar as estruturas (Fases 1-7)

Esta metade decide o quê é relevante na página. Ela nunca lê nada do HTML original diretamente — trabalha sobre uma cópia sanitizada (Fase 1) e devolve Family objects cujos elementos ainda apontam para essa cópia. A ponte de volta ao documento original só é construída na Parte 2.

1 · Sanitização estrutural — sanitize/

strip.sanitize() faz um copy.deepcopy() da árvore antes de tocar nela — o original nunca é mutado, e essa cópia intocada é o que a Fase I (ancoragem) vai precisar depois. Sobre a cópia: remove script, style, svg, noscript, comentários, meta, link, e trunca data-URIs inline para um placeholder curto (mantendo o atributo, já que sua presença pode importar estruturalmente, sem pagar o custo de tokens do base64).

Atributos ruidosos (style, handlers on*, atributos visuais legados como bgcolor/cellpadding) são removidos por denylist, não allowlist — mais seguro que arriscar descartar um data-* customizado que uma etapa posterior precise.

boilerplate.py remove navegação/menus/sidebars/breadcrumbs (por tag, role ou palavra-chave em classe/id) e widgets ocultos por display:none inline — mas nunca por atributo hidden ou classe de ocultação via CSS externo, porque sites reais usam isso para paginação client-side de conteúdo real (ver decisão sobre paginação oculta).

2 · Dedup de subtree idêntico — sanitize/dedup_subtree.py

Colapsa subtrees byte-a-byte idênticos repetidos em escala (ex. um ícone SVG de compartilhar repetido 484× num site de notícias) num <template-ref> + contagem, quando o número de repetições passa de DEFAULT_MIN_COUNT = 50 — limiar propositalmente alto, acima do maior registro real do corpus (100 manchetes no folhadesp), para nunca engolir um conteúdo genuinamente repetido (ver por quê).

_serialize() exclui o atributo data-d2p-uid do hash — sem isso, o carimbo único que a Fase I grava em cada elemento tornaria toda subtree única e desligaria esta etapa por completo (medido: folhadesp caiu de 1520 remoções para 0).

3 · Fingerprint estrutural com fallback — fingerprint/structural.py

compute_fingerprint() tenta, em ordem de prioridade:

data-testid → role → classes semânticas → id (só se reutilizado) → aria-* → tag + forma dos filhos

id só conta como identidade quando o documento o reutiliza em mais de um elemento (reused_ids()) — por convenção HTML um id é único por elemento, então tratá-lo como identidade padrão faria toda instância de um registro parecer única e destruiria a clusterização. É mantido como fallback para o caso (inválido mas real) de uma página reusar um id como classe de fato (#btnDownloadUrl ×28 em acervodadostecnicosgovbr.html).

Classes CSS "atômicas" (estilo Stylex/CSS-in-JS, ex. x78zum5) e atributos de hash de build uniformes (ex. data-v-444d5111 do Vue scoped CSS) são filtrados na comparação — são artefatos de compilação, não identidade semântica. O detalhamento de quais classes contam como identidade está no interlúdio abaixo, porque a resposta ficou mais interessante do que "óbvio" depois de medida contra páginas reais.

fingerprint_key() descarta children_tags do fingerprint sempre que a identidade já é específica (testid/role/classe/id) — dois div.textoItem com números diferentes de filhos ainda contam como "o mesmo tipo de nó" (tolerância a campo opcional). Só quando a identidade caiu para ("shape",) — nenhum sinal semântico — é que a tupla de tags-filhas entra na chave, senão toda tabela sem classe da página colapsaria num cluster só.

4 · Content signature — content/signature.py + content/classifiers.py

Cada campo de texto é classificado sempre a partir do próprio texto, nunca da classe CSS — a mesma classe CSS pode carregar um FILE_FORMAT num card e um COUNT_LABELED no vizinho:

Temporais
DATETIME DATE TIME
Numéricos
MONEY CURRENCY INTEGER DECIMAL PERCENTAGE
Estruturados
EMAIL URL PHONE BOOLEAN
Específicos do projeto
FILE_FORMAT COUNT_LABELED
Genéricos
TEXT EMPTY

Degrada graciosamente: texto que não bate em nenhum padrão específico vira TEXT (nunca força um tipo errado nem lança exceção). MONEY aceita o valor com ou sem símbolo de moeda grudado — match_money() tira o prefixo/sufixo antes de testar as regexes de duas casas decimais, porque toda listagem de preço do corpus público (£51.77) o carrega junto, ao contrário da fatura bancária, onde a moeda mora numa coluna própria.

5 · Clusterização tolerante — cluster/siblings.py

Dois níveis, porque estrutura DOM sozinha não basta — é a própria conclusão do estudo de caso do Banco do Brasil na spec original:

  1. Estrutural (group_by_fingerprint) — agrupa por fingerprint. Campos opcionais não fragmentam o grupo.
  2. Por assinatura de conteúdo (content_signature_sequence) — dentro de um grupo estrutural idêntico, sub-agrupa pela sequência de tipos dos filhos diretos. É assim que uma linha de transação (DATE|TEXT|CURRENCY|MONEY) se separa de uma linha de categoria (EMPTY|TEXT|EMPTY|EMPTY) mesmo quando ambas são tr(td,td,td,td) sem nenhuma classe distintiva.

optional_field_presence() mede, para descendentes com identidade semântica (não ("shape",)), em quantos elementos do cluster cada um aparece — optional_fields() filtra para os que aparecem em parte mas não em todos, que é o material bruto do optional_fields exibido na saída.

6 · Ranking de relevância — cluster/rank.py

O componente mais heurístico do projeto. Contagem bruta de repetição não indica relevância — um menu de navegação rotineiramente se repete mais que a tabela de dados real. score_cluster() combina:

  • Diversidade de tipos de conteúdo informativos (campos com DATE/MONEY/etc. pontuam mais que TEXT/EMPTY puros)
  • Número de sub-campos semanticamente distintos por registro
  • Palavras-chave de contêiner ancestral (bônus: result/row/item; penalidade: nav/menu/sidebar)
  • Tamanho de texto do próprio registro (log-amortecido)

Todos os sinais são limitados em profundidade (SIGNAL_MAX_DEPTH = 3) e amostrados em no máximo MAX_ELEMENTS_SAMPLED = 20 elementos — um sinal recursivo irrestrito faria um contêiner genérico grande "herdar" a riqueza de tudo que está aninhado dentro dele e vencer o registro real que ele envolve.

cluster/families.py agrupa clusters do mesmo fingerprint e mesmo caminho de ancestral (location_key) numa Family só, atribuindo papéis (primary/section/summary/ empty/variant, em cluster/roles.py) — é o que impede que as 12 linhas de categoria de uma fatura, que sozinhas pontuariam baixo, sejam descartadas mesmo compartilhando o formato exato das 122 linhas de transação que são selecionadas.

7 · Sampling representativo — sampling/representative.py + cluster/outliers.py

Primeiro, segundo, meio, penúltimo, último — mais outliers reais: valor numérico mínimo/máximo por posição de campo (ex. o maior débito de uma fatura) e o registro com texto mais curto/mais longo. Capado por max_samples_per_cluster (padrão 7), com as posições representativas mantidas primeiro se precisar cortar.

Interlúdio — o que conta como identidade

Três funções em fingerprint/hashattrs.py decidem se um token de classe é identidade, e cada uma existe por causa de uma classe de erro medida numa página real — não de uma regra abstrata pensada antes.

FunçãoRejeitaPágina que forçou
looks_like_atomic_class_tokenclasse gerada (Stylex x78zum5, literais de bug false/true)WhatsApp Web — 5-25 classes atômicas por elemento
looks_like_state_class_tokenclasse de estado transiente (is-hidden, has-error, active)Folha — is-hidden partia 100 manchetes em 70+30
looks_like_utility_class_tokenclasse de layout (Bootstrap/Tailwind/Primer: col-md-3, mb-5, no-underline, f3)Books to Scrape, GitHub Topics — utilitária vencia a classe semântica real

semantic_class_tokens() é o funil por onde fingerprinting e path passam — filtra as três. discriminating_class_tokens() é a exceção deliberada: ela mantém classes de estado, porque uma classe de estado é inútil para responder "o que é este elemento?" e ideal para responder "o que separa este grupo daquele?" — é o que permite a síntese de seletor propor li.item:not(.is-hidden).

A lista de classes utilitárias é lexical, de propósito. A hipótese óbvia — "utilitária aparece espalhada por muitas tags e contextos, semântica marca um tipo de elemento num lugar só" — foi medida contra o corpus inteiro e não se sustenta: no-underline aparece 41 vezes numa única tag sob um único pai, e toctree-l1 aparece 40 vezes numa única tag sob um único pai. Não há sinal estrutural no documento que separe as duas; a diferença é que um vocabulário é publicado por um framework de CSS e o outro é do autor da página. A lista é, portanto, uma lista de palavras — errada nas bordas, do mesmo jeito que looks_like_atomic_class_token — e isso está registrado no código (hashattrs.py) para que ninguém gaste outra tarde procurando a versão estrutural.

Um id passa por regra parecida em fingerprint/structural.py::generated_ids(), usada só na síntese de seletor (Fase J): um id é gerado quando pertence a uma família grande de mesmo prefixo de dois caracteres e o que vem depois é um token curto e opaco — mw+hg, 0A, B_k (Parsoid da Wikipédia). Separador não resolve isso, embora pareça que deveria: os tokens do Parsoid são base64url e carregam -/_ próprios. Medido: 6671 dos 7699 ids de um artigo são marcados, enquanto term-*, section-*, main-* e score_* ficam intactos. Um id gerado nunca ancora um seletor — no lugar dele entra uma âncora posicional (table:nth-of-type(2)).

Parte 2 — Sintetizar o parser (Fases I-M)

A saída da Parte 1 descreve uma estrutura repetida mas não a endereça: diz que a posição 1 tem um DATE, nunca que a posição 1 é td.tituloLancamento; e o path_display não serve como seletor (truncado, com máscaras *, derivado da árvore sanitizada). As cinco fases seguintes fecham esse buraco, sempre voltando ao documento original.

I · Ancoragem — anchor.py

stamp_uids(root) grava um data-d2p-uid incremental em cada elemento do documento original, antes da sanitização copiar a árvore — o deepcopy da Fase 1 leva o carimbo junto, então todo elemento da cópia sabe exatamente qual elemento do original lhe deu origem. build_index() monta o mapa uid → elemento original; to_original()/originals_for() resolvem um elemento (ou lista) da cópia de volta. Elementos destruídos pelo dedup de subtree (Fase 2) viram <template-ref> sem carimbo — originals_for() os descarta silenciosamente, porque um placeholder nunca teve fingerprint específico e jamais seria candidato a família.

J · Fecho, promoção e seletor de registro — parser/records.py + parser/selector.py

Uma Family não é o registro, por dois motivos medidos, não presumidos:

  • Ela é incompleta. O agrupamento por conteúdo (Fase 5) abandona linhas que classificam de forma atípica — no Banco do Brasil, duas transações comuns cuja descrição começava com dígito viraram COUNT_LABELED, formaram cluster de tamanho 1 e caíram abaixo de min_cluster_size. A família tinha 152 das 154 linhas reais. closure(family, clean_root) recalcula o conjunto puramente por structural_identity — o par (fingerprint normalizado, location_key) — devolvendo todo elemento do documento que compartilha essa identidade, não só os que sobreviveram ao agrupamento por conteúdo.
  • Ela é profunda demais. content_signature_sequence lê o texto dos filhos diretos, então o ranking prefere o nível mais fundo em que os filhos ainda diferem — tipicamente um wrapper interno do registro, não o registro. Medido: a sobreposição entre os elementos da família e os elementos do registro real (ground truth escrito à mão) era exatamente zero em quatro das seis páginas originais. promote(elements) resolve isso.

promote() sobe a árvore, nível por nível, com uma regra de parada que olha para os pais:

  • Pais distintos (cada elemento tem seu próprio pai) → sobe, é só mais um nível do mesmo registro.
  • Pais compartilhados, poucos elementos por pai (no máximo MAX_PARTS = 4, e ao menos MIN_FANOUT_PARENTS = 3 pais distintos) → sobe também. Esse é o fan-out para baixo: cada linha de conversa do WhatsApp são dois div irmãos sem identidade (ícone, texto) dentro do registro real; sem esta regra a subida parava exatamente um nível abaixo do registro, porque "pai compartilhado" também é o sinal de "cheguei ao contêiner da coleção". O que distingue as duas situações é o tamanho do fan-out: 46 divs colapsam em 23 pais de dois em dois; 154 linhas de fatura colapsam em 2 tbody de 77 em 77. Dois pais não bastam (MIN_FANOUT_PARENTS) — senão duas tabelas pequenas de três linhas cada virariam um "registro" de tbody.
  • Pai compartilhado, muitos por pai, ou só dois pais → para. Isto é o contêiner da coleção; o nível anterior é o registro.

Cada nível promovido precisa ser re-fechado antes do próximo ser escalado a partir dele (completed_levels()) — subir pode revelar elementos que a semente original não cobria (o WhatsApp tem uma linha de "conversas trancadas" fora da lista virtualizada, com o mesmo data-testid mas location_key diferente das outras 22), e só olhando o pai desse elemento adicional é que a subida sabe que ainda não chegou à fronteira certa. closure_of() também trata data-testid como independente de localização — é marcador de tipo de componente, vale o mesmo onde quer que o componente esteja montado — mantendo identidade por classe exigindo localização igual (div.limites > div.textoItem continua diferente de div.totalFatura > div.textoItem).

Entre os níveis com seletor exato, o critério de escolha é: o mais externo que ainda carregue identidade própria (testid ou classe semântica) — _has_identity() em parser/build.py. Isso resolve o empate entre dois invólucros 1:1: em books.toscrape.com, article.product_pod está dentro de um li sem classe; ambos selecionam os mesmos vinte elementos, mas um humano chamaria o article de registro, e é ele que carrega identidade.

parser/selector.py::synthesize(targets, root, generated_ids) faz a busca:

  1. Gera candidatos a partir da identidade compartilhada pelos alvos: data-testid/id (exato ou por prefixo comum, cobrindo o caso * mascarado pela Fase de path), combinações de classes semânticas (tamanho 3→1), tag pura.
  2. Ancora em até MAX_ANCESTOR_LEVELS = 4 níveis de ancestral, com combinador descendente e filho direto — o filho direto é o que resolve o caso do WhatsApp, onde o combinador descendente sozinho casava divs em profundidades diferentes.
  3. Refina candidatos que casam demais com :not(.classe), usando discriminating_class_tokens (que mantém classe de estado) tanto no próprio elemento quanto nos ancestrais — é como se chega em li.c-headline:not(.is-hidden).
  4. Ids marcados por generated_ids() nunca entram como predicado de atributo.
  5. Ordena candidatos do menor para o maior, com a tag pura sempre por último (uma tag sem qualificador funciona hoje e quebra no dia em que um segundo elemento do mesmo tipo aparecer na página), e para no primeiro que bate recall 1.0 e precisão 1.0.

Critério de aceitação assimétrico. Recall 1.0 é obrigatório — um registro que o seletor não alcança é um registro que o parser nunca devolve, em silêncio. Precisão abaixo de 1.0 é medida e reportada mas não decide sozinha: quem decide o que fazer com a sobra é o parser/build.py, que só emite o registro se achar um candidato com as duas em 1.0; senão a estrutura vai para failures com os near_misses medidos.

K · Locator e nome de campo — parser/fields.py + parser/naming.py

discover(records, span) encontra os campos comuns a todos os registros — nunca a partir de records[0] sozinho: _representative_indices() escolhe o registro de forma modal (filhos e netos), mais o mais largo quando difere. Isso importa porque numa tabela cujo primeiro registro é a própria linha de cabeçalho (th), usar só ele geraria locators th:nth-of-type(k) que nunca resolvem nas linhas de dado.

Um elemento é candidato a campo (_candidate_fields) quando é uma folha de texto (_is_text_leaf) ou carrega um atributo de captura. A regra de folha é a mais sutil do módulo:

  • Um filho de bloco com texto sempre faz do elemento um contêiner (nunca uma folha).
  • Um filho inline (a, span, code, em...) só conta como parte da prosa quando o texto próprio do elemento supera o dos filhos inline — uma definição de glossário com dois links é um valor só; mas o td.title do Hacker News, cujo texto inteiro está em span.titleline + span.sitebit, tem dois sub-campos rotulados, não um.
  • Um filho cujo texto inteiro é um símbolo isolado (is_decoration — o ¶ de um permalink) não conta nem para um lado nem para outro.

_locator_candidates() gera, em ordem de estabilidade: identidade própria (itemprop, data-testid, classe semântica), ancorado num ancestral intermediário (por identidade ou por posição — o h3 acima de um título, a célula de uma tabela), e posicional puro como último recurso. Um locator sem ancestral vira > tag:nth-of-type(k) — a forma "filho direto" do Selectors 4 — porque p:nth-of-type(1) sozinho compila para um XPath descendant:: e também encontrava o primeiro parágrafo de caixas de nota aninhadas dentro da definição, perdendo o parágrafo principal por ambiguidade.

_capture_attrs() decide entre texto e atributo: a→href, img→src, time→datetime, mais title quando presente (onde um card guarda a versão não truncada de um texto visível). Um elemento que tem as duas coisas (texto e atributo) vira dois campos, com a coluna de atributo herdando o nome da coluna de texto mais um sufixo (titulo / titulo_url).

naming.py::element_name() é a cascata de nomes, andando do elemento do campo até (mas não incluindo) o elemento do escopo:

itemprop → data-testid → aria-label → classe semântica → tag com significado HTML (dt/dd/time/img/...) → tipo+posição

Cada passo só é aceito se a evidência for constante entre os registros (_constant_across) — um nome descreve a coluna; valor que muda por registro é dado, não nome. Sem essa checagem, o aria-label de um card de notícia (que carrega a manchete daquele card) virava o nome do campo inteiro. Quando nada na cascata resolve, o nome cai para tipo_posição (date_1, money_4) e um humano renomeia editando o ParserSpec.

table_header_cells() lê nomes de uma linha <th> de verdade quando os registros são linhas de uma tabela — mapeando pela célula ancestral do valor, não só pela célula bruta, para que um valor aninhado (td > a) ainda receba o nome da sua coluna. header_names() é o caso irmão: um cabeçalho escondido entre os próprios registros, com células td — o caso do Banco do Brasil, onde a linha ['Data','Transações','Moeda','Valor'] é, estruturalmente, mais uma linha da tabela.

_prune() descarta campo-furniture: um valor idêntico em todos os registros, sem atributo de captura, classificado como TEXT/EMPTY — o botão "Acessar o recurso" repetido em cada card. A coluna R$ constante de uma fatura sobrevive porque classifica como CURRENCY, não TEXT. Um valor visto numa única ocorrência (MIN_FIELD_PRESENCE = 2) também é descartado — a mesma barra que min_cluster_size usa para estrutura, aplicada a campo.

Registro espalhado por irmãos — span

Em três padrões do corpus um registro não é um elemento: é vários irmãos consecutivos. Um item do Hacker News são três <tr> (título, subtexto, espaçador); uma entrada de glossário é dt+dd. period(anchors) corta os filhos do contêiner comum em cada âncora — os segmentos resultantes repetem um padrão ((tr,tr,tr), (dt,dd)); o comprimento modal é o span, e um segmento pode terminar mais cedo (dois termos dividindo uma definição) mas nunca ultrapassar o padrão.

A família pode ter caído no membro errado do período — a dd, não a dt — e emparelhar cada definição com o próximo termo seria silenciosamente errado. anchor_offsets(anchors) ordena os deslocamentos candidatos pela quantidade de identidade (testid, classe, id) que cada posição do período carrega; shift_anchors() aplica o deslocamento, e o resultado é re-fechado e re-verificado (seletor exato outra vez) antes de period() ser consultado de novo — só assim o termo órfão (sem definição própria) entra no conjunto. Cada FieldEntry carrega sibling: a qual elemento do segmento seu locator é relativo (scoped_element(), em fields.py, nunca atravessa para o segmento seguinte).

L · O parser serializado — parser/spec.py

ParserSpec é dado, não código: dataclasses congeladas (RecordEntry, FieldEntry) serializáveis em YAML ou JSON, com schema_version. Nada aqui passa por exec() — o executor interpreta o seletor com cssselect/lxml e o locator com XPath relativo, nunca compila string arbitrária como código Python.

M · Executor e validação — parser/executor.py + parser/validate.py

execute(spec, html) reanalisa o HTML original do zero — nunca reaproveita a árvore da compressão — e devolve um Extraction por tipo de registro. compile_record() compila o seletor e os XPaths dos campos uma vez só; record_values() resolve cada campo relativo ao elemento de escopo certo (scoped_element, respeitando sibling). Registros são skipados, nunca descartados: cada um carrega skipped/skip_reason (all_empty — linha totalmente vazia — ou header_values — bate com o cabeçalho literal que nomeou os campos), porque quem recebe 139 de 154 linhas não tem como distinguir um descarte deliberado de um locator quebrado sem essa informação.

validate() devolve a contagem de presença e a conformidade de tipo por campo — reaproveitando content/signature.py::classify(), o mesmo classificador que decidiu o tipo do campo durante a síntese, agora rodado sobre o valor extraído de verdade. Um campo declarado MONEY cujos valores pararam de classificar como MONEY é sinal de que o locator escorregou para o elemento errado — o tipo de falha que uma checagem de mera taxa de preenchimento não pega.

Como isso é verificado

examples/ guarda 7 páginas reais com dado pessoal (faturas, conversas) e é .gitignored — a maior parte da suíte só roda na máquina de quem tem os arquivos. corpus/ é o contraponto commitado: 11 páginas públicas sem dado pessoal, cada uma escolhida por um modo de falha específico (id gerado pelo Parsoid, rowspan, fan-out lateral, fan-out para baixo, classe utilitária sem semântica nenhuma, valor por instância em aria-label...) — ver a tabela completa.

corpus/ground_truth.yaml registra, por página, o que um humano extrairia; tests/test_corpus.py mede quatro coisas contra isso:

  • registro — o conjunto de elementos do seletor sintetizado bate com o do ground truth (ou é um invólucro 1:1 dele);
  • nomes — os nomes que a própria página fornece foram de fato derivados;
  • quantidade de campos — onde a página não nomeia nada, quantos valores por registro saíram;
  • valores — a extração devolve valores lidos à mão da marcação. É a única checagem que separa "o seletor e os nomes parecem certos" de "o dado saiu certo" — pega locator que escorregou para um invólucro, valor colado no vizinho, título truncado na forma visível quando o completo está num atributo.

Toda lacuna conhecida vira pytest.mark.xfail(strict=True) com a razão medida no código — nunca uma asserção afrouxada. Consertar a lacuna faz o teste passar inesperadamente, o que quebra a suíte até o marcador ser removido: a correção tem que ser notada.
