Instalação

Ainda não publicado no PyPI — instale a partir do repositório clonado:

git clone https://github.com/bonafe/DOM2parser.git
cd DOM2parser

python3 -m venv .venv
source .venv/bin/activate

pip install -e .
O ambiente do host pode ser externally-managed (PEP 668) — o venv acima é obrigatório, não opcional, em distros recentes (Debian/Ubuntu).

Quickstart

import dom2parser

html = open("pagina.html", encoding="utf-8").read()
result = dom2parser.compress(html)

print(result.text)
# REPEATED STRUCTURES (ranked by relevance):
#
# tr > td > div.lancamentos > table > tbody > tr
#   selector: div.lancamentos tr  # matches 154, covers all 154
#   fields:
#     data: td:nth-of-type(1)        # DATE, present in 125/154
#     transacoes: td:nth-of-type(2)  # TEXT, present in 141/154
#     moeda: td:nth-of-type(3)       # CURRENCY, present in 128/154
#     valor: td:nth-of-type(4)       # MONEY, present in 128/154
#   skip header row: ['Data', 'Transações', 'Moeda', 'Valor']
#   row types:
#     [primary] count: 122
#       signature: DATE | TEXT | CURRENCY | MONEY
#       examples:
#         ['28/07', 'PGTO DEBITO CONTA...', 'R$', '-11.966,18']  # numeric-outlier
#     ...

print(result.reduction["reduction_pct"])
# {'chars': 97.3, 'tokens': 97.3}

Os nomes data, transacoes, moeda e valor não foram inventados nem pedidos a um modelo: foram lidos da linha de cabeçalho da própria fatura.

Retorna um CompactRepresentation:

CampoTipoDescrição
.textstrRepresentação em texto estruturado.
.jsondictMesma informação em JSON (schema 2).
.reductiondictContagem de chars/tokens original vs. compacto e % de redução.
.parserParserSpecO parser verificado, pronto para executar contra o HTML original.

Formato JSON (schema 2)

Uma forma só para toda estrutura. O schema 1 tinha duas, mutuamente exclusivas (plana quando a família tinha um membro e nenhum contêiner, aninhada caso contrário), distinguidas apenas por quais chaves estavam presentes, e examples[].value era str ou list[str] conforme o tamanho da assinatura. Quem consumia precisava ramificar nas duas. Agora container está sempre presente e pode ser nulo, members é sempre lista, e values é sempre um objeto. 

{
  "schema_version": 2,
  "structures": [{
    "path_display": "tr > td > div.lancamentos > table > tbody > tr",
    "record_selector": {
      "selector": "div.lancamentos tr",
      "span": 1,
      "verified": {"matched": 154, "expected": 154, "precision": 1.0, "recall": 1.0}
    },
    "container": {"path_display": "... > div.lancamentos", "count": 2},
    "fields": [
      {"name": "data", "locator": "td:nth-of-type(1)", "type": "DATE",
       "capture": "text", "attribute": null, "required": false,
       "present": 125, "total": 154, "name_source": "header_row", "sibling": 0}
    ],
    "members": [{
      "role": "primary", "count": 122,
      "signature": ["DATE", "TEXT", "CURRENCY", "MONEY"],
      "examples": [{"values": {"data": "28/07", "transacoes": "PGTO DEBITO...",
                               "moeda": "R$", "valor": "-11.966,18"},
                    "reasons": ["representative-position", "numeric-outlier"]}],
      "optional_fields": {"img[class=seloBronze]": {"present": 6, "total": 10}},
      "rank_score": 15.04
    }]
  }],
  "failures": []
}

path_display não é um seletor. Ele é truncado em seis níveis sem sinalizar truncamento, e um * dentro de um segmento (div[data-testid="list-item-*"], tr#tx-*) marca a parte de um id/testid que varia por instância — índice de lista virtualizada, id de banco, slug. Serve para um humano localizar a estrutura lendo. Quem endereça é record_selector.selector, que foi medido contra o documento original.

Quando fields está vazio (a estrutura não teve campos descobertos), values carrega o texto do elemento sob a chave _text — o tipo nunca muda. E failures lista as estruturas cujo seletor casava demais sem regra explicando a sobra, com os quase-acertos medidos; elas nunca viram registro.

span é quantos irmãos consecutivos formam um registro — 3 num item do Hacker News (tr.athing + linha de subtexto + espaçador), 2 num glossário (dt + dd). O seletor casa o primeiro deles, e cada campo diz em sibling a qual elemento do segmento seu locator é relativo (0 é a âncora). Um locator vazio é o próprio elemento do escopo — a dd que é a definição inteira — e um locator iniciado por > é filho direto. Ver ADR-010.

Executando o parser

O ParserSpec é dado, não código — executado por lxml, nunca por exec(). Ele roda contra o HTML original, nunca contra a forma compacta: 

from dom2parser.parser.executor import execute
from dom2parser.parser.validate import validate

record = result.parser.records[0]
extraction = execute(result.parser, html)[record.name]

print(validate(record, extraction).as_text())
# registros encontrados: 139   (154 casados: 2 cabeçalhos e 13 linhas vazias pulados, cada um com o motivo)
# com data: 123
# com transacoes: 139
# com moeda: 126
# com valor: 126

print(extraction.kept[3].values)
# {'data': '28/07', 'transacoes': 'PGTO DEBITO CONTA...', 'moeda': 'R$', 'valor': '-11.966,18'}

extraction.records traz tudo que o seletor casou; extraction.kept tira o que foi descartado por regra (a linha de cabeçalho). Nada é removido em silêncio — cada registro carrega skipped e skip_reason, porque quem recebe 153 de 154 linhas não tem como distinguir um descarte deliberado de um locator quebrado.

result.parser.to_yaml() serializa e ParserSpec.from_yaml() recarrega — é o ponto onde um humano renomeia um campo cujo nome saiu ruim (name_source: type_position indica exatamente esses).

CLI de teste/demo

Um wrapper fino existe para inspecionar o pipeline manualmente durante o desenvolvimento — não é a interface principal do projeto, que é a biblioteca: 

python -m dom2parser.cli caminho/para/pagina.html

Desenvolvimento

# setup
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# rodar toda a suíte (inclui regressão contra os 6 exemplos reais em examples/)
pytest -q

# spike isolado de avaliação do HtmlRAG (ver decisions.html#adr-001)
python scripts/measure_htmlrag.py examples/bancodobrasil.html

A suíte de testes usa tests/fixtures/ground_truth.yaml como gabarito: para cada uma das 6 páginas reais em examples/, anota qual seletor CSS corresponde ao conteúdo relevante e qual corresponde ao ruído dominante conhecido (menu, widget de filtro, JSON de bootstrap). tests/test_eval_harness.py é a suíte de regressão principal do projeto: verifica que o ranking sempre coloca o conteúdo relevante acima do ruído conhecido nas 6 páginas.
